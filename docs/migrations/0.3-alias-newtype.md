# Alias and newtype migration

TypeRB now separates transparent aliases from nominal newtypes in source
syntax:

```trb
alias LoadResult<T> = Result<T, LoadError>
newtype UserId = Integer
newtype ProductIds = Array<ProductId>
```

The former `type Name = Target` spelling reports a migration error. Do not
replace every declaration mechanically. Classify each use by meaning:

- use `alias` for shorthand, Result specializations, unions, and collection
  names whose values should remain interchangeable with the target;
- use `newtype` for identifiers, codes, quantities, and other domain values
  that must not be mixed with their representation or another domain type.

For a newtype, construct and unwrap explicitly:

```trb
user_id := UserId.new(raw_id)
raw_id := user_id.value()
```

A newtype target may be any concrete, fully instantiated, non-nullable type.
`newtype ProductIds = Array<ProductId>` is supported. Generic declarations such
as `newtype Id<T> = T`, nullable representations such as
`newtype MaybeId = Integer?`, and validated or fallible custom constructors are
not part of this release. Write optional values as `UserId?`.

Ordinary TypeRB calls remain nominal. Built-in JSON codecs, `trb/web` binding,
Jobs payloads, and ORM value parameters are typed representation boundaries and
do not require repetitive unwrapping. Use `.value()` for other external APIs
unless their package declaration explicitly defines the same boundary.

Backends may erase the physical wrapper in generated output. Nominality is a
TypeRB source and typed-IR guarantee, not an ABI promise for handwritten Go,
Ruby, or TypeScript code.
